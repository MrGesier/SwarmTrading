# SwarmTrade V0.3 — Multi-Scale Alpha Architecture
## Targeted upgrade specification for the current Codex build

This specification is based on the current V0.2 implementation:
- `backend/engine.py`
- `backend/main.py`
- `backend/analysis.py`
- React frontend in `frontend/src/`

The current implementation is visually strong and structurally clean, but its horizon selector is not yet a true multi-timescale forecasting engine.

---

## 0. Current issue observed in the code

Today:
- returns are horizon-specific: 1s / 5s / 30s / 60s / 180s,
- but trade flow is always computed over the last 30 seconds,
- volatility is computed from recent sampled returns over about 60 seconds,
- microprice is instantaneous,
- weighted book imbalance is instantaneous,
- the global market-intent score combines all horizons plus the same flow/book state,
- effective strategy weights are learned across the whole 320-genome population,
- selected horizon mainly scopes displayed strategies and selected consensus.

Therefore the 180s horizon is not a complete 180s market state.
It is largely a 180s return normalized using shared short-term context.

The main V0.3 objective is:

> **Every forecasting horizon must have its own market memory, feature state, strategy swarm, calibration, entropy, effective strategy count, and trade probability.**

# 1. Separate three concepts that are currently conflated

Never use one UI control to mean all three.

## A. Display interval
How candles are drawn.

Examples:
- 1s
- 5s
- 30s
- 1m
- 3m
- 15m

This should affect the chart only.

## B. Prediction horizon
How far into the future the model is trying to forecast.

Examples:
- 1s
- 5s
- 30s
- 3m
- 15m
- 1h

This changes the model target and all horizon-specific features.

## C. Context horizon
Longer market regime used as a prior.

Example for a 3m prediction:
- child context: 30s
- local horizon: 3m
- parent context: 15m

The user should be able to view 1-minute candles while asking the model for a 3-minute forecast.

# 3. Use time-decay, not only hard windows

For a feature observation \(x_i\) at time \(t_i\), create an exponentially decayed state:

\[
\bar{x}_h(t)
=
\frac{
\sum_i x_i \exp[-(t-t_i)/\tau_h]
}{
\sum_i \exp[-(t-t_i)/\tau_h]
}
\]

with:

\[
\tau_h \propto h
\]

Example half-lives:

```python
HALF_LIFE = {
    1: 0.5,
    5: 2.5,
    30: 15,
    180: 90,
    900: 450,
    3600: 1800,
}
```

Hard rolling windows are still useful for extrema and exact cumulative quantities.
Use both:
- rolling integral,
- exponentially decayed state.

This creates memory without discontinuities at window boundaries.

# 4. Path memory instead of snapshots

A 3-minute model should not ask only:

> What is book imbalance now?

It should know:

> Has the bid been dominant for most of the last 3 minutes?

Add:

\[
Persistence_h
=
\frac{1}{h}
\int_{t-h}^{t}
I(signal(u) > 0)\,du
\]

Also calculate:
- mean signal,
- median signal,
- slope,
- maximum,
- minimum,
- time above zero,
- run length,
- impulse integral.

Example:

```text
Book imbalance now       +0.11
3m mean                  +0.36
3m slope                 +0.08/min
Bullish duty cycle        78%
Longest bullish run       91 sec
```

That describes an actual 3-minute state.

# 5. Rebuild order-flow features at every horizon

The current fixed 30-second flow should disappear.

For every horizon \(h\):

\[
TFI_h
=
\frac{
V^{buy}_h - V^{sell}_h
}{
V^{buy}_h + V^{sell}_h + \epsilon
}
\]

Also implement event-level OFI using bid/ask price and quantity changes.

For each horizon store:

```text
OFI level
OFI EWMA
OFI slope
OFI acceleration
OFI persistence
OFI surprise relative to recent baseline
```

Research has repeatedly found that order-flow imbalance is more informative than raw volume for short-horizon price impact, while recent BTC evidence also warns that the predictive effect is small and unstable enough to require walk-forward validation.

---

# 6. Add pressure-versus-capacity

Raw flow is not enough.

Define directional pressure divided by the market's capacity to absorb it.

Example:

\[
Toxicity^{sell}_h
=
\frac{
AggressiveSellVolume_h
}{
NearTouchBidCapacity_h + \epsilon
}
\]

and symmetrical buy toxicity.

Also calculate:
- flow / depth,
- flow / replenishment,
- flow / expected depth,
- price impact per unit flow.

This is more useful than static imbalance alone.

# 7. Each horizon gets its own swarm

Instead of one 320-strategy weight vector, maintain:

```python
swarm[horizon]
```

Each swarm has:
- local strategies,
- local rolling signal history,
- local correlation matrix,
- local \(N_{eff}\),
- local entropy,
- local calibrated weights,
- local performance by regime.

Example:

```text
3m horizon

Raw genomes       96
Active            83
N_eff             12.4
LONG support      7.8
SHORT support     2.3
Neutral           2.3
Swarm entropy     0.48
```

Do not allow a 1-second strategy to affect 3-minute \(N_{eff}\) merely because it exists in the same global matrix.

# 8. Hierarchical decorrelation

Use two stages.

### Stage 1 — within each horizon
Decorrelate strategies inside 3m, inside 30s, etc.

### Stage 2 — across horizon consensus
Decorrelate the horizon-level predictions themselves.

This prevents:
- 8 momentum variants,
- repeated over 6 horizons,

from becoming dozens of artificial votes.

# 9. Consensus term structure

Define:

\[
C(h,t)
\]

where \(h\) is prediction horizon.

Example:

```text
1s      +0.82
5s      +0.71
30s     +0.48
3m      +0.16
15m     -0.11
1h      -0.27
```

This is a **term structure of market intent**.

Calculate:

\[
\frac{\partial C}{\partial \log h}
\]

and:

\[
\frac{\partial^2 C}{\partial (\log h)^2}
\]

Also track:
- number of sign changes,
- nearest zero crossing,
- alignment score,
- curvature.

# 10. Signal Propagation Front

This should become one of SwarmTrade's signature concepts.

Suppose consensus evolves:

```text
time      1s    5s    30s    3m
t0       -.2   -.3   -.4    -.5
t1       +.5   -.2   -.4    -.5
t2       +.7   +.4   -.2    -.5
t3       +.8   +.6   +.3    -.3
t4       +.7   +.7   +.5    +.1
```

The bullish signal is **propagating from micro to macro**.

Define a front:

\[
h^*(t): C(h^*,t)=0
\]

Track the velocity of that front.

```text
Propagation:
1s → 5s → 30s → 3m

Front velocity: expanding
Direction: bullish
```

This is potentially more informative than any single-horizon score.

Opposite situation:

```text
1s     +0.8
5s     +0.6
30s    -0.4
3m     -0.7
```

This may be a bounce inside a larger bearish state rather than a true reversal.

# 14. Do not predict only “up or down”

Use trading targets.

For horizon \(h\), estimate:

\[
P(
UpperBarrier\ hit\ before\ LowerBarrier
\mid X_t
)
\]

within the next \(h\) seconds.

The barrier size should include execution economics.

Example:

```text
3m forecast

P(+12 bp before -8 bp)       61%
P(-8 bp before +12 bp)       24%
P(neither within 3m)         15%
```

This is far more actionable than:

```text
P(return > 0) = 58%
```

# 30. Horizon-aware event decay

Each event should have a state:

\[
NewsImpact(t)
=
Impact_0 e^{-(t-t_0)/\tau_{event}}
\]

But \(\tau\) depends on event type.

Examples:
- breaking hack/exchange outage: fast and possibly persistent,
- ETF-flow headline: slower,
- social chatter: noisy,
- FOMC/CPI surprise: immediate plus longer digestion.

Learn decay empirically.

# 35. Hawkes / event-excitation engine

The current tool measures current pressure.

Add a model of whether events trigger more events.

For event types:
- aggressive buy,
- aggressive sell,
- bid placement,
- ask placement,
- bid cancellation,
- ask cancellation,
- price uptick,
- price downtick,
- liquidation.

# 36. Pressure impulse response

For every market event type estimate:

\[
IRF(\tau)
=
E[r_{t+\tau} \mid event_t] - baseline
\]

```text

5s      +3.0 bp
```

# 40. Multi-task forecasting

Instead of training six completely isolated models, eventually train a shared temporal encoder with horizon-specific heads:

\[

\rightarrow
\begin{cases}
Head_{1s}\\
Head_{5s}\\
Head_{30s}\\
Head_{3m}\\
Head_{15m}\\

\]

This allows common structure while preserving horizon-specific predictions.

Multi-horizon forecasting literature supports predicting a path of horizons rather than one isolated future point.

# 41. Horizon consistency regularization

Do not force all horizons to agree.

But penalize impossible/noisy forecast geometry.

Examples:
- abrupt 1s probability changes are acceptable,
- abrupt neighboring 3m/5m contradictions should be less common unless evidence supports a regime change.

The model can learn smoothness over log horizon while allowing sign changes.

# 43. Cross-horizon alignment score

Define a weighted alignment around selected horizon.

For selected \(h\):

\[
A_h =
\sum_j
k(\log(h_j/h))
\, sign(C_h)
\, C_{h_j}
\]

Use a kernel giving nearby horizons greater importance.

A 3m signal confirmed by 30s and 15m gets higher confidence than an isolated 3m signal.

# 44. Contradiction is information

# 54. Central design rule

For a selected horizon \(h\), every feature should answer one of three questions:

### Local state
What has happened over a time scale appropriate to \(h\)?

### Context
What do slower horizons imply about the environment in which this trade would occur?

### Timing
What do faster horizons imply about whether now is a good moment to enter?

Never mix the three blindly.

---

# 55. Desired end state

Selecting **3 minutes** should mean:

> “Given the full state of the market accumulated over relevant sub- and super-horizons, what is the probability that a 3-minute LONG, SHORT, or NO-TRADE decision has positive expected value after costs, and is now a good entry time?”

It should NOT mean:

> “Use a 3-minute return but keep mostly the same instantaneous book and 30-second flow features.”

That is the core V0.3 upgrade.

# SwarmTrade V0.2 — Product & System Specification
## Market Intent Engine / Strategy Swarm Terminal

### 1. Product thesis

SwarmTrade is not an indicator dashboard. It is a real-time market-state inference system designed to answer four questions:

1. **What is the market doing now?**
2. **Which independent strategy families are converging, and how fast?**
3. **At which nearby price/volatility/liquidity states will large groups of strategies flip?**
4. **Is the order book already creating a low-resistance path toward those trigger states?**

The terminal therefore visualizes not only price, but also:
- market microstructure,
- liquidity geometry,
- strategy population state,
- entropy / regime state,
- simulated trigger surfaces,
- early consensus formation,
- expected execution cost and adverse selection.

The key design principle is **anticipation before confirmation**.

- Frontend: `http://localhost:3000`
- Backend: `http://localhost:8000`

# 7. EFFECTIVE STRATEGY COUNT

200 strategies are not 200 independent opinions.

For a rolling strategy-return or signal correlation matrix with eigenvalues λ:

\[
N_{eff} =
\frac{(\sum_i \lambda_i)^2}
{\sum_i \lambda_i^2}
\]

The UI should always show:

```text
Raw strategies:        240
Active strategies:     213
Effective strategies:   37.4
```

and:

```text
Raw LONG votes:          169
Effective LONG support:  28.2
```

This protects the engine from fake consensus caused by hundreds of parameter variations of the same idea.

# 8. SWARM ENTROPY

Let family-level or decorrelated strategy probabilities be \(p_i\).

Normalized entropy:

\[
H_S =
-\frac{\sum_i p_i \log p_i}
{\log K}
\]

Interpretation:

- high \(H_S\): fragmented strategy population
- low \(H_S\): convergence
- falling \(H_S\): convergence is forming
- rising \(H_S\): consensus is dissolving

Display:

```text
Swarm Entropy
1.0 ┤
0.8 ┤─────╮
0.6 ┤     ╰──╮
0.4 ┤        ╰────╮
0.2 ┤             ╰────
0.0 ┴────────────────────
                     NOW
```

More important than level:
- \(dH_S/dt\)
- \(d^2H_S/dt^2\)

# 11. CROWD SHADOW ENGINE

This is one of the central innovations.

At every update, the engine asks:

> If the market moved to a nearby state, which strategies would change position?

The naive version varies only price.

The advanced version varies:
- price,
- volatility,
- spread,
- order-flow imbalance,
- depth,
- time,
- volume,
- funding,
- OI.

For strategy \(i\):

\[
S_i(x)
\]

where \(x\) is the hypothetical future market state.

The engine evaluates:

\[
\Delta S_i(x) = S_i(x) - S_i(x_0)
\]

and aggregates decorrelated weighted flips.

# 15. LIQUIDITY × TRIGGER INTERACTION

This is the real “one step ahead” model.

For each trigger zone, calculate the resistance of the path from current price.

Conceptually:

\[
R(p) =
\int_{p_0}^{p}
L(u) du
\]

where \(L(u)\) represents executable opposing liquidity.

Then combine:

\[
IgnitionPotential(p)
=
\frac{TriggerDensity(p)}
{PathResistance(p) + \epsilon}
\]

A dense trigger cluster behind a thin order book is more dangerous/interesting than a dense cluster behind enormous liquidity.

# 20. FRAGILITY SCORE

A consensus can be strong but fragile.

Counterfactual test:

> How much must market state change before the current swarm consensus collapses?

Let \(x_0\) be current state.

Estimate minimal perturbation:

\[
F =
\min_{\delta}
||\delta||
\quad
\text{s.t.}
\quad
sign(C(x_0+\delta)) \neq sign(C(x_0))
\]

UI:

```text
Consensus: +0.72
Fragility: HIGH

Only -4.2 bp or OFI -0.18 would destroy current LONG consensus.
```

This is a critical risk metric.

# 45. WHY NOT STREAMLIT AS THE FINAL UI?

Streamlit is excellent for:
- prototype,
- parameter experiments,
- research pages.

It is less suitable as the final low-latency trading terminal because SwarmTrade requires:
- dense realtime updates,
- several independently refreshing panels,
- custom heatmaps,
- high-frequency interaction,
- potentially WebGL/Canvas drawing.

Therefore:

```text
Research UI       Streamlit optional
Production UI     React/Next.js
Backend           Python/FastAPI
```

# 52. STRATEGY DISCOVERY ENGINE

A future component can systematically create candidate strategies from feature primitives.

Example grammar:

```text
SIGNAL :=
  FEATURE
  FEATURE - FEATURE
  zscore(FEATURE)
  slope(FEATURE)
  acceleration(FEATURE)
  rank(FEATURE)
  FEATURE × FEATURE
```

Filters:

```text
REGIME CONDITION
LIQUIDITY CONDITION
VOLATILITY CONDITION
TIME CONDITION
```

Then evaluate candidates with strict out-of-sample controls.

The goal is not to create millions of overfit strategies.

The goal is to discover **orthogonal hypotheses**.

---

# 53. STRATEGY NOVELTY SCORE

For candidate \(i\):

\[
Novelty_i =
1 -
\max_j |\rho(i,j)|
\]

or a more robust embedding-distance score.

High-performing but redundant strategies receive lower priority.

# 54. INFORMATION DECAY

For each signal, estimate how predictive power changes with horizon.

Example:

```text
OFI signal:
250 ms     strong
1 s        strong
5 s        moderate
30 s       weak
5 min      none
```

The engine should learn the **half-life of information**.

This determines:
- holding period,
- entry urgency,
- execution style.

I_t =

# 71. CENTRAL PRODUCT IDEA

The platform should visually answer:

> **Where is the market structurally likely to become self-reinforcing?**

It observes:
1. what market participants are doing,
2. what systematic strategies are doing,
3. what would cause those strategies to change state,
4. how much liquidity separates price from those state changes,
5. whether entropy is increasing or collapsing,
6. whether the resulting move would still have edge after execution costs.

This is the conceptual core of the Market Intent Engine.
